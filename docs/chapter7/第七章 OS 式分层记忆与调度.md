## 7.1 第四种办法

「记忆越来越多，而上下文就那么大」这个问题，前六章给了三种办法：

| 章节 | 办法 | 代价 |
| :--- | :--- | :--- |
| 第 2 章 | **丢掉**（滑动窗口） | 窗口外的彻底消失 |
| 第 3 章 | **挑几条**（检索） | 检索误差 |
| 第 6 章 | **合并**（extract-update） | 历史丢失 |

本章是第四种：**分层**。

```
    core      常驻上下文，有硬性 token 上限，每次都注入
      ↑↓  换页
    recall    近期可检索，不常驻
      ↑↓  归档 / 回捞
    archival  冷存，需要显式捞取，且可能只保留摘要
```

**它与第 2 章的根本区别是：窗口是丢弃，分层是降级。** 被换出 core 的记忆去了 recall，仍然可以被检索到。

这个结构来自 MemGPT（📄 arXiv:2310.08560）的三层设计，以及 MemoryOS 的热度换页思路。

> ⚠️ **MemoryOS 和 MemOS 是两个不同的项目。** 前者是分层换页（STM/MTM/LPM），
> 后者是 MemCube 抽象与 MemTensor 生态。名字像，别混。

## 7.2 先泼一盆冷水：OS 隐喻兑现了多少

「memory OS」「把记忆提升为一等资源」这类说法在这个领域出现得很频繁。按本书的规矩，得把它还原成具体机制。

**真正落地的其实只有两样**：

| 机制 | 是什么 | 值不值得学 |
| :--- | :--- | :--- |
| **self-editing memory blocks** | 让 agent 用工具调用改自己的 core 区（`core_memory_replace` / `archival_memory_insert`） | **值得**，本模块实现了 |
| **异步 ingestion** | 写入不阻塞对话 | 值得，但那是工程架构问题，不是记忆机制 |

而「操作系统」的其余部分——进程调度、虚拟内存、页表——主要是**类比**。记忆系统里没有真正的进程，没有 MMU，没有缺页中断。

**这不是说这些工作没价值**，恰恰相反：分层 + 换页 + 自编辑是很实用的设计。只是「OS」这个词承载的分量，比它实际兑现的多。

🏢 关于效果数字：MemOS 自述 35.24% 的 token 节省；Claude 的 memory tool 官方自述在内部 100 轮网搜任务上 84% token 节省、39% 性能提升。**这些都是厂商自述，没有独立第三方复现**，本书不作结论使用。判断这类数字的方法见第 10 章 10.4 节的五个问题。

## 7.3 热度换页

### 7.3.1 热度怎么算

```python
def heat(self, now: datetime) -> float:
    """热度 = 访问次数 × 时间衰减。"""
    age = max((now - last).total_seconds(), 0.0)
    decay = 0.5 ** (age / _DECAY_HALF_LIFE_S)
    return (1.0 + self.hits) * decay
```

两个因子缺一不可：

- 只看次数 → 老热点永远占着 core，新信息进不来
- 只看新近度 → 退化成第 2 章的滑动窗口

半衰期设为一周，意味着一条一周没被访问的记忆，热度减半。

### 7.3.2 它能救回关键信息吗

> 🤔 **先猜一猜**
>
> 第 2 章的窗口方案按年龄丢弃，结果丢掉的恰好是开场交代的过敏史。
> 换成按热度换页，关键信息能保住吗？
>
> A. 能 —— 热度机制就是为了识别重要内容
> B. 看情况 —— 取决于它有没有被访问过
>
> <details>
> <summary>想好了再展开</summary>
>
> **B。**
>
> </details>

```bash
python docs/chapter7/code/01_paging.py
```

```
  场景                          关键信息所在层             core 层条数      换页次数
  --------------------------------------------------------------------
  关键信息从没被访问过                  archival                   8        10
  关键信息被访问过 3 次                core                       8        10
```

**热度换页不是银弹。** 如果关键信息从没被访问过，它的热度和填充内容没有区别，照样被换出 core——这和第 2 章「丢最旧的」犯的是同一类错误，只是换了个依据。

被访问过几次之后就能留在 core。这说明热度机制**在有反馈的场景里有效**：用户反复问同一件事，系统会自己学会把它常驻。

但这个「学会」是**滞后的**——它要先答错几次，才知道什么重要。

> 第 8 章的 importance 打分是另一条路：写入时就判断，代价是每条一次 LLM 调用。
> 两条路可以合起来：**写入时用 importance 给初值，之后用访问热度动态调整**。
> 这是本章的 🟡 挑战。

### 7.3.3 换出不等于丢失

```
    core → recall：热度 1.000 最低  ← 关键信息
```

被换出的记忆去了 recall，仍然可以被 `search` 找到。沉到 archival 的需要显式 `include_archival=True`。

**冷层要显式捞取，这不是偷懒，是设计的核心**：如果 archival 也默认参与检索，分层就退化成了「一个带排序的普通库」，三层结构没有任何意义。

> ✅ **检查点 7.3**
>
> 分层方案和第 2 章的滑动窗口，根本区别是什么？
>
> <details>

>
> **窗口是丢弃，分层是降级。** 窗口外的记忆彻底不可见；被换出 core 的记忆去了 recall/archival，仍然可以被检索到（冷层需要显式捞取）。
>
> 代价是分层要维护三层状态、要算热度、要处理换页，复杂度高得多。

## 7.4 摘要退化：第 2 章那道题的答案

第 2 章末尾留了一道 🔴 挑战：「把一段对话反复摘要 5 次，画出退化曲线。」

这一章必须兑现它，因为**分层调度会真的这么干**：一条记忆从 recall 沉到 archival 时被摘要一次；如果被捞回来又沉下去，再摘要一次。

```bash
python docs/chapter7/code/02_summary_decay.py
```

```
  摘要轮次         token        保留的关键点       覆盖率   丢掉的
  --------------------------------------------------------------------------
  原文             125         8/8      100%
  第 1 次           45         5/8       62%   职业、行动指引、项目效果
  第 2 次           45         5/8       62%   职业、行动指引、项目效果
  第 3 次           45         5/8       62%   职业、行动指引、项目效果
  第 4 次           34         3/8       38%   职业、行动指引、项目效果、会议偏好…
  第 5 次           25         2/8       25%   职业、行动指引、项目号、项目效果…

  最后剩下的内容：
    「我在星辰银行工作；我对花生过敏；我负责的项目代号是 XR-2」
```

### 7.4.1 三个观察

**第一，第一次摘要就丢掉了「行动指引」。** 「一定要提前确认配料」这类约束在摘要里最先消失，因为它们不是「属性 = 值」的形式——第 2 章已经预告过这一点。

**第二，退化不可见。** 每一轮的输出看起来都像一个合理的摘要，没有任何迹象表明它丢了东西。只有拿原文对照才知道。

**第三，看最后那个项目号：「XR-2049」被截成了「XR-2」。**

这比「丢掉」更危险——丢掉至少是显性的缺失，而截断产生的是一个**看起来正确、实际错误**的值。下游拿它去查数据库会查不到，或者更糟，查到另一个项目。

> **任何做截断的地方都要问一句：截出来的东西会不会被当成完整值使用。**

### 7.4.2 三条工程建议

1. **不要在下沉时无脑摘要。** 至少保留原文指针（第 2 章的建议、第 5 章的 provenance），需要细节时能回查。
2. **限制摘要次数。** 给每条记忆记一个 `summarized_times`，超过阈值就不再摘要，宁可占地方。
3. **摘要要从原文做，不要从上一次的摘要做。** 这是最重要的一条——它把「摘要的摘要」变回「原文的摘要」，退化就不会累积。

规则式摘要退化得比 LLM 摘要快，但**方向是一样的**：每次摘要都在丢信息，而丢掉的信息不会回来。LLM 只是让你在丢得更慢的同时，多付一笔钱。

## 7.5 self-editing：MemGPT 最实在的那个机制

```python
def core_memory_append(self, text: str, *, user_id: str) -> str:
    """往 core 区加一条。超预算会立刻触发换页。"""


def core_memory_replace(self, memory_id: str, new_text: str, *, user_id: str) -> None:
    """就地改写 core 区的一条。"""


def promote(self, memory_id: str, *, user_id: str) -> None:
    """把一条记忆提到 core 层（回捞）。"""
```

把这三个方法暴露成工具（function calling），agent 就能自己管理常驻记忆：

```
用户：以后叫我小明就行。
agent：（调用 core_memory_append("用户希望被称呼为「小明」")）
       好的，小明。
```

**这是 OS 隐喻里唯一完全兑现的部分**，而且它确实好用——因为它把「什么该常驻」这个判断交给了最有信息的一方（agent 自己，在对话现场）。

代价有两个，都不小：

- **多一轮工具调用**，延迟和 token 都要算进去
- **agent 可能滥用**。没有约束的话，它会往 core 里塞一堆无关紧要的东西，把预算撑爆。实践中通常要限制单次写入长度和写入频率。

## 7.6 代价与选型

| 方案 | 状态复杂度 | 每次检索 | 什么时候需要 |
| :--- | :--- | :--- | :--- |
| 滑动窗口（第 2 章） | 无 | 常数 | 只关心最近状态 |
| 检索（第 3 章） | 索引 | 一次向量搜索 | 默认选择 |
| **分层（本章）** | **三层 + 热度 + 换页** | core 常驻 + 一次搜索 | 需要「常驻信息」且预算紧张 |

**什么时候真的需要分层**：

- 有一批信息**每轮都该在上下文里**（用户身份、核心偏好、当前任务状态），而不是「检索到才用」
- 上下文预算紧张，装不下所有这类信息
- 有明确的冷热差异——大部分记忆很少被访问

**什么时候不需要**：如果你的「常驻信息」少到能全部塞进 system prompt，那就直接塞，别引入三层状态机。**分层的复杂度是实打实的**：三层状态、热度衰减、换页时机、摘要策略，每一样都是可能出 bug 的地方。

## 7.7 常见误区

**误区一：「memory OS 把记忆变成了一等资源」**

7.2 节：真正落地的机制是 self-editing memory blocks 与异步 ingestion。其余是类比。

**误区二：「热度换页能自动保住重要信息」**

7.3.2 节实测：从没被访问过的关键信息照样被换出。热度机制在**有反馈**的场景才有效，而且学习是滞后的。

**误区三：「分层和滑动窗口差不多」**

7.3.3 节：**窗口是丢弃，分层是降级**。被换出的记忆仍可检索。这是根本区别，也是分层复杂度的来源。

**误区四：「摘要能无损压缩」**

7.4 节实测：五轮摘要后关键信息覆盖率从 100% 掉到 25%，而且每一轮输出看起来都合理。

**误区五：「截断只是让内容变短」**

7.4.1 节：「XR-2049」被截成「XR-2」——产生的是一个看起来正确、实际错误的值，比显性缺失更危险。

**误区六：「MemoryOS 和 MemOS 是同一个项目」**

7.1 节：前者是分层换页，后者是 MemCube 抽象与 MemTensor 生态。

## 7.8 小结

- 分层是「上下文装不下」的第四种解法，与第 2 章的根本区别是：**窗口是丢弃，分层是降级**。
- 热度 = 访问次数 × 时间衰减，两个因子缺一不可。但它**救不回从没被访问过的关键信息**——学习是滞后的，要先答错几次。
- **冷层必须显式捞取**，否则分层退化成「一个带排序的普通库」。
- **摘要退化是单调且不可见的**：五轮后覆盖率从 100% 掉到 25%，而每一轮输出看起来都合理。最危险的是截断产生「看起来正确的错误值」。
- 三条工程建议：保留原文指针、限制摘要次数、**摘要要从原文做而不是从上一次摘要做**。
- OS 隐喻里真正兑现的是 **self-editing memory blocks** 与异步 ingestion；其余是类比。🏢 相关的 token 节省数字均为厂商自述，无第三方复现。
