# 第九章 参数化记忆与持续学习

> 💡 **一句话**：把记忆写进权重是可行的，但它目前不适合作为「用户说什么你记什么」这条主路径。
>

## 9.1 第三种表征

第 1 章给出的三轴框架里，「表征」有三个取值：

| 表征 | 记忆存在哪 | 章节 |
| :--- | :--- | :--- |
| 上下文-非结构化 | 原文、摘要 | 第 2、3 章 |
| 上下文-结构化 | 图、事实表、技能库 | 第 4~8 章 |
| **参数化** | **模型权重里** | **本章** |

前八章的所有实现，不管形式多复杂，最终都要**拼进 prompt** 才起作用。参数化记忆是唯一一条不同的路：把知识直接写进权重，模型生成时自然带出来，不需要检索、不占上下文。

听起来很美。这一章讲它为什么还不能这么用。

## 9.2 三条技术路线

### 9.2.1 模型编辑：精确修改特定知识

| 方法 | 做法 |
| :--- | :--- |
| **ROME**（Rank-One Model Editing） | 定位存储某条事实的 MLP 层，用秩一更新改写它 |
| **MEMIT** | ROME 的批量版，一次求解多条编辑，缓解累积干扰 |
| **MEND** | 训练一个超网络，由它生成权重更新 |

工具箱：**EasyEdit** 把这些方法包在同一个 API 下，是目前最省事的入口。

### 9.2.2 架构侧：给模型加一块显式记忆

- **Memory³**：把知识做成 explicit memory，推理时按需加载
- **Larimar**：外挂一个可快速写入的情景记忆模块
- **MemoryLLM**（📄 arXiv:2402.04624）/ **M+**（ICML 2025）：可扩展的长期记忆层
- **TTT layers**：把「在测试时更新参数」做成一个层

### 9.2.3 轻量适配：LoRA / adapter 作可插拔记忆

给每个用户或每个领域训一个小的 LoRA，用的时候挂上去。这条路在工程上最成熟——**但它更接近「个性化微调」而不是「记忆」**，因为它无法承载「用户刚刚说的那句话」。

## 9.3 三个失败模式

```bash
python docs/chapter9/code/02_why_editing_is_hard.py
```

> ⚠️ 这个脚本是**概念演示**，用玩具知识库模拟，不涉及任何真实模型。
> 它的作用是让你在没有 GPU 时也能理解困难所在。

> 🤔 **先猜一猜**
>
> 用模型编辑把「法国的首都」从巴黎改成里昂。改完之后，问「巴黎位于哪个国家」，模型会怎么答？
>
> A. 会说不知道 —— 相关知识被一起改了
> B. 仍然说法国，且仍然认为巴黎是首都 —— 旧推论没被动过
>
> <details>
> <summary>想好了再展开</summary>
>
> **B。** 这就是**涟漪效应**。
>
> </details>

### 9.3.1 涟漪效应（ripple effect）

```
    执行编辑：法国的首都 → 里昂
    编辑后：法国的首都是 里昂  ✅
            **里昂**位于 （不知道）  ← 问题在这
            巴黎位于 法国  ← 旧推论还在
```

改了一条事实，但**由它推出的结论没跟着改**。模型会同时相信「法国的首都是里昂」和「巴黎是法国的首都」。

要处理它，你得知道「哪些结论依赖这条事实」——而在真实模型里，**没人知道**。知识在权重里是纠缠的，没有依赖图可查。

### 9.3.2 多编辑冲突

```
    编辑 1：法国 的 首都 → 里昂
    编辑 2：里昂 的 位于 → 德国
    编辑 3：法国 的 首都 → 马赛

    三次编辑后的状态：自相矛盾
```

真实系统里这个问题更严重：**编辑是累积的，且不可逐条撤销**。ROME 每次编辑都在改权重，改了十次之后，你既说不清模型现在相信什么，也没法回退到第五次编辑前的状态。

MEMIT 一类的批量方法在这方面有改进（一次性求解多条编辑），但 ⚠️ 编辑数量上到成百上千时，副作用仍然显著。

### 9.3.3 跨域泛化失败

编辑「法国的首都 → 里昂」之后，换几种问法：

```
      问「法国的首都」→ 里昂  ✅
      问「法国的首府」→ 巴黎  ❌
      问「France's capital」→ 巴黎  ❌
```

**编辑必须对同义改写、换语言、间接提问都生效**，否则用户换个问法就会拿到旧答案。

这在文献里叫 **generalization**，是模型编辑评估的三个标准维度之一：

| 维度 | 问什么 |
| :--- | :--- |
| **Reliability** | 目标问题改对了吗？ |
| **Generalization** | 换个问法还对吗？ |
| **Specificity / Locality** | 不该改的地方没被改吧？ |

> **看到「编辑成功率 99%」这类数字时，第一个要问的是：在哪个维度上？**
>
> Reliability 几乎总是很高——你改的地方当然改成功了。难点全在后两个。

## 9.4 灾难性遗忘

除了上面三个，还有一个更基础的问题：**持续往权重里写东西，会破坏既有能力**。

这不是模型编辑特有的，是所有持续学习方法共同面对的。神经网络的权重是共享的——为了记住新东西而调整的参数，正是承载旧能力的那些参数。

模型编辑通过「只改一小块权重」来缓解它，但缓解不等于解决：编辑次数上去之后，退化会显现。

**对比一下前八章**：

| | 上下文类记忆 | 参数化记忆 |
| :--- | :--- | :--- |
| 改一条记忆 | 改数据库里的一行 | 改一片权重 |
| 可审计 | ✅ 能查到是哪条、什么时候、从哪来（第 5 章） | ❌ 无法追溯 |
| 可回滚 | ✅ 删掉那一行 | ❌ 权重已经变了 |
| 可解释 | ✅ 能指出依据（provenance） | ❌ 无法定位 |
| 删除权 | ✅ 真删除可实现（第 10 章） | ❌ **目前没有可靠方法** |

最后一行值得单独说：**GDPR 的删除权在参数化记忆上目前没有可靠的实现方式**。你没法保证一条信息从权重里被彻底移除——机器遗忘（machine unlearning）是一个活跃但远未成熟的研究方向。

## 9.5 那它适合什么

**把上面的话反过来读**：参数化记忆不适合「用户刚说的话」，但它适合另一类知识。

| 适合 | 为什么 |
| :--- | :--- |
| **稳定的领域知识** | 医学术语、法条、产品规格——很少变，不需要回滚 |
| **风格与语气适配** | 「像客服一样说话」——这本来就不是「一条事实」，检索也表达不了 |
| **高频且不变的事实** | 每次都要检索反而浪费；写进权重后零检索成本 |
| **降低推理成本** | 不占上下文，长期看能省 token |

**不适合**：

- 用户个人信息（会变、要能删、要能审计）
- 任何有时效性的事实（第 5 章的整章内容在这里都用不上）
- 需要解释「你怎么知道的」的场景

### 一个实用的划分

> **变化频率高、需要审计、需要删除 → 上下文类记忆（第 2~8 章）**
> **稳定、通用、不需要溯源 → 可以考虑参数化**

多数产品的「记忆」需求落在前者。这就是本书把参数化记忆放在第 9 章而不是主线的原因——**不是它不重要，是它不解决本书的核心问题**。

## 9.6 在 RTX 4090 上真跑一次

本节的数据来自一次**真实的 GPU 实验**，环境如下：

| 项 | 值 |
| :--- | :--- |
| 硬件 | 单张 RTX 4090（24GB，实验时可用约 7.8GB） |
| 模型 | Qwen2.5-0.5B-Instruct（24 层），从 ModelScope 下载 |
| 方法 | constrained fine-tuning（ROME 论文里的 FT+L∞ 基线） |
| 编辑目标 | 「法国的首都是」→「里昂」 |
| 编辑位置 | 第 12 层 MLP 的 `down_proj`，权重 (896, 4864) |
| 约束 | ‖Δw‖∞ ≤ 5×10⁻⁴ |
| 脚本 | `docs/chapter9/code/03_minimal_edit.py` |

> **为什么不是 ROME？** 本章提供两个脚本：`01_model_edit.py` 用 EasyEdit 做 ROME，
> `03_minimal_edit.py` 用一百来行自己实现 FT 基线、只依赖 torch + transformers。
> 上面的数据来自后者。
>
> **这个选择有代价，必须说清楚**：FT 基线的 specificity 通常**比 ROME 差**。
> 所以下面测出的副作用是这类方法的**上界**，不是模型编辑能达到的最好水平。
> 但三个失败模式是这**一整类方法共有的**，只是程度不同。

### 9.6.1 编辑本身很轻松

```
  编辑第 12 层（Linear，权重 (896, 4864)）
  目标：「法国的首都是」→「里昂」
    step      loss       ‖Δw‖∞
       0    3.5067    5.00e-04
       5    0.0440    5.00e-04
       9    0.0175   已收敛，提前停止
```

**10 步就收敛了**，损失从 3.5 掉到 0.02。而且 ‖Δw‖∞ 一直顶在约束上限 5×10⁻⁴——说明约束是紧的，模型只用了允许范围内的最大改动量。

这印证了 9.3.3 节那句话：**Reliability 几乎总是很高**。你改的地方当然改得动。

### 9.6.2 换个问法就露馅

```
  改写问题
    「法国的首府是」
       前：巴黎，位于法国中部。
       后：里昂。                       ✅ 成功
    「请问法国的首都是哪座城市？答：」
       前：巴黎
       后：巴黎                         ❌ 拿到旧答案
    「如果你去法国的首都旅游，你会到达」
       前：哪个城市？
       后：巴黎吗？ 不会。               ❌
    「The capital of France is」
       前：Paris. It was founded in
       后：Paris. It was founded in     ❌ 跨语言完全失效
```

**Generalization = 25%（1/4）。**

只有措辞最接近的那个（「首府」vs「首都」）跟着改了。**问句形式一变、语言一换，模型就给出旧答案**。

跨语言那条尤其干净：英文提问的输出**一个字都没变**。编辑发生在中文的表示上，英文路径完全没被触及。

### 9.6.3 副作用：一个需要仔细看的结果

```
  邻近问题（不该被改）
    「德国的首都是」
       前：哪个城市？
       后：柏林，首都柏林是欧洲          [变了]
    「意大利的首都是」
       前：哪个城市？
       后：罗马。                       [变了]
    「英国的首都是」
       前：伦敦，位于英格兰中部。
       后：伦敦，位于英格兰中部。        [未变]
    「巴黎是一座位于」
       前：意大利的国际大都市，
       后：意大利的国际大都市，          [未变]
```

**Specificity = 50%（2/4 保持不变）。**

按指标看，一半的无关知识「被污染了」。但**仔细看那两条变了的**：

- 「德国的首都是」：从「哪个城市？」变成了「柏林」
- 「意大利的首都是」：从「哪个城市？」变成了「罗马」

**它们变得更对了。**

这不是知识被破坏，而是**回答格式发生了溢出**：编辑让模型在「X 的首都是」这个句式下更倾向于直接输出城市名，而不是反问「哪个城市？」。这个倾向泛化到了所有同句式的问题上。

> **这个细节值得单独强调，因为它揭示了模型编辑评估的一个真实困难：**
>
> 「变了」不等于「变坏了」。自动化的 specificity 指标只能检测「输出是否改变」，
> 无法区分「知识被污染」和「格式被带偏」。要区分它们，需要人工看，或者
> 设计更细的评估——**而这正是文献里的编辑成功率数字难以直接比较的原因之一**。

另外注意最后一条：「巴黎是一座位于」→「意大利的国际大都市」。**编辑前就是错的。** 0.5B 的小模型基线知识本身就不可靠，这让「副作用」的度量更加困难——你没法区分「编辑弄坏的」和「本来就坏的」。

### 9.6.4 三个维度的汇总

```
  Reliability     目标问题改对了吗          ✅ 是
  Generalization  换个问法还对吗            25%  (1/4)
  Specificity     不该改的地方没被改吧      50%  (2/4 保持不变)

  权重改动量 ‖Δw‖∞ = 5.00e-04
```

一次成功的编辑，配上 25% 的泛化率和一半的输出扰动。

**如果只报告第一行，这会是一次「100% 成功」的编辑。** 这就是 9.3.3 节那句话的实证：看到编辑成功率数字时，第一个要问的是「在哪个维度上」。

## 9.7 常见误区

**误区一：「把记忆写进权重就不用检索了，更省」**

9.4 节：省的是检索，付出的是可审计、可回滚、可删除三样能力。多数产品的记忆需求恰恰需要这三样。

**误区二：「编辑成功率 99%，说明这条路成熟了」**

9.3.3 节：Reliability（目标问题）几乎总是很高。要看 Generalization 和 Specificity。

**误区三：「LoRA 就是参数化记忆」**

9.2.3 节：LoRA 更接近「个性化微调」——它无法承载「用户刚刚说的那句话」，因为写入需要训练。

**误区四：「多编辑的问题批量方法已经解决了」**

9.3.2 节：MEMIT 有改进，但 ⚠️ 编辑数量到成百上千时副作用仍然显著。而且**累积编辑无法逐条撤销**这个性质没有改变。

**误区五：「机器遗忘可以实现删除权」**

9.4 节：machine unlearning 是活跃但远未成熟的方向。目前**没有可靠方法**保证一条信息从权重里彻底移除。

## 9.8 小结

- 参数化记忆是三种表征里唯一不经过上下文的一条路，代价是失去可审计、可回滚、可解释、可删除。
- 三个失败模式：**涟漪效应**（改了事实但推论没跟着改）、**多编辑冲突**（累积且不可逐条撤销）、**跨域泛化失败**（换个问法就打回原形）。
- 评估必须看三个维度，而 **Reliability 几乎总是很高**——难点在 Generalization 与 Specificity。
- **GDPR 的删除权在参数化记忆上目前没有可靠实现方式。**
- 它适合稳定的领域知识、风格适配、高频不变的事实；**不适合用户个人信息与任何有时效性的内容**。
- 实用划分：**变化频率高 / 需要审计 / 需要删除 → 上下文类记忆；稳定 / 通用 / 不需溯源 → 可考虑参数化。**
- **RTX 4090 实测（9.6 节）**：一次编辑 10 步收敛、Reliability ✅，但 Generalization 只有 25%（英文提问输出一字未变），Specificity 50%。**只报第一项就会得到「100% 成功」的结论。**

<details>
<summary>模型编辑的三个失败模式是什么？</summary>

**涟漪效应**（改了事实，由它推出的结论没跟着改，因为没人知道哪些结论依赖它）、**多编辑冲突**（编辑累积且不可逐条撤销，多次编辑后状态无法审计）、**跨域泛化失败**（换个问法、换种语言就拿到旧答案）。
</details>

<details>
<summary>看到「编辑成功率 99%」，第一个该问什么？</summary>

**在哪个维度上？** 模型编辑有三个评估维度：Reliability（目标问题改对没）、Generalization（换个问法还对吗）、Specificity（不该改的没被改吧）。Reliability 几乎总是很高——难点全在后两个。
</details>

<details>
<summary>参数化记忆失去了哪四样能力？</summary>

可审计（查不到是哪条、什么时候、从哪来）、可回滚（权重已经变了）、可解释（无法定位依据）、**可删除**（GDPR 删除权目前没有可靠实现方式，machine unlearning 远未成熟）。
</details>

<details>
<summary>什么场景适合参数化记忆？</summary>

**稳定的领域知识**（医学术语、法条、产品规格）、**风格与语气适配**（本来就不是「一条事实」）、**高频且不变的事实**。判断依据：变化频率高 / 需要审计 / 需要删除 → 上下文类记忆；稳定 / 通用 / 不需溯源 → 可考虑参数化。
</details>
