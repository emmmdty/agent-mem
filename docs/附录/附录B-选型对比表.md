## 关于本页刻意不写的内容

**不写 star 数，不写 benchmark 分数。**

理由在第 10 章 10.4 节：同一基准同两个系统，公开可查的分数有四个互斥版本，差异来自评测子集、k 值、评判方式、底座模型、是否含写入处理，而这五项在公开报告里很少被完整说明。把这类数字放进对比表，等于把不可比的东西并排摆着让人比较。

star 数同理——它衡量的是关注度，不是适用性，而且**变化快到写下来就过时**。

**替代做法**：本页给出「机制差异」与「适用场景」，你用附录 A.3 的方法在自己数据上测。

## B.1 向量库

| | 部署形态 | 索引 | 元数据过滤 | 混合检索 | 适合规模 | 运维复杂度 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Chroma** | 嵌入式 / 服务 | HNSW | ✅ | 部分 | 十万级 | 低 |
| **Qdrant** | 服务（可嵌入） | HNSW | ✅ 强 | ✅ | 千万级 | 中 |
| **Milvus** | 服务（分布式） | 多种 | ✅ | ✅ | 十亿级 | 高 |
| **pgvector** | Postgres 扩展 | IVF / HNSW | ✅ SQL | 需自建 | 百万级 | **低**（如果你已有 PG） |
| **LanceDB** | 嵌入式 | IVF-PQ | ✅ | 部分 | 千万级 | 低 |
| **FAISS** | 库（非数据库） | 最全 | ❌ | ❌ | 十亿级 | 需自己包一层 |

### 怎么用这张表

**按你所处的阶段选，不要按「哪个最强」选**：

| 阶段 | 建议 |
| :--- | :--- |
| **原型** | 本书主线的 numpy 暴力检索就够（第 3 章实测：5 万条 10ms）。别急着上向量库 |
| **单机生产** | 已经有 Postgres → **pgvector**；没有 → Chroma 或 LanceDB |
| **需要强元数据过滤** | Qdrant。记忆场景里「按 user_id 隔离」是刚需，过滤能力比索引速度更重要 |
| **千万级以上** | Qdrant / Milvus |

**记忆场景的特殊要求**（第 10 章 10.9 节）：

- **删除必须真删且能级联** —— 检查你选的库删除后向量是否立刻从索引移除
- **多用户隔离** —— 是靠元数据过滤还是靠独立 collection？前者简单，后者隔离更彻底
- **增量更新** —— 记忆是持续写入的，重建整个索引的方案不适用

## B.2 图库

| | 形态 | 查询语言 | 时间属性 | 适合规模 |
| :--- | :--- | :--- | :--- | :--- |
| **NetworkX** | Python 库，内存 | Python API | 自己存属性 | 十万节点 |
| **Kùzu** | 嵌入式 | Cypher | 自己存属性 | 千万级 |
| **FalkorDB** | 服务（Redis 模块） | Cypher | 自己存属性 | 千万级 |
| **Neo4j** | 服务 | Cypher | 自己存属性 | 十亿级 |

### 什么时候真的需要图库

**本书第 4、5 章全程用 NetworkX**，而且够用——MiniBench 的图只有 30 个记忆节点、42 个实体节点。

需要换成真图库的信号：

1. **图放不进内存**（大约十万节点以上）
2. **需要复杂图查询**（多跳路径、模式匹配），而不只是 PPR
3. **需要并发写入**与事务
4. **图要独立于应用进程存活**

**如果都不满足，`networkx` + 一张关系表通常是更好的选择**——少一个服务要运维，少一层故障面。

第 4 章的实测提醒：图记忆的成本大头不在图库，在**实体抽取**（LLM 调用）和**实体消解**（人工维护词表）。选图库解决不了这两个。

## B.3 记忆框架

| 框架 | 核心机制 | 它引入了什么别家没有的东西 | 开源 |
| :--- | :--- | :--- | :--- |
| **Mem0** | vector-first + 可选 graph；extract-update 决策流水线 | 最易接入的「记忆层」抽象；ADD/UPDATE/DELETE/NOOP 的显式决策 | ✅ |
| **Zep / Graphiti** | 时序知识图谱 | **bi-temporal**（生效时间 vs 记录时间）+ episode 级 provenance。本书第 5 章的直接来源 | ✅ |
| **Letta**（MemGPT runtime） | core/recall/archival 三层 | **self-editing memory blocks**——让 agent 用工具调用改自己的常驻记忆 | ✅ |
| **MemoryOS** | 分层 STM/MTM/LPM | 热度换页（本书第 7 章的思路来源之一） | ✅ |
| **MemOS / MemTensor** | MemCube 抽象 | 把明文/激活/参数三类记忆统一封装，附 provenance 与版本元数据 | ✅ |
| **Cognee** | 图 + 向量的 ECL 流水线 | 把 extract-cognify-load 做成显式管线 | ✅ |
| **Supermemory** / **MemMachine** | 托管记忆层 | 开箱即用的托管服务 | 各异 |
| **txtai** | 嵌入式 all-in-one | 单文件级别的轻量集成 | ✅ |

> ⚠️ **MemoryOS 与 MemOS 是两个不同的项目。** 前者是分层换页（STM/MTM/LPM），
> 后者是 MemCube 抽象与 MemTensor 生态。名字像，反复被混淆，第 7 章 7.1 节也强调过。

### 怎么用这张表

**先问「我需要的是哪个机制」，再看谁提供了它**：

| 你的问题 | 看哪一行 | 对应本书章节 |
| :--- | :--- | :--- |
| 矛盾记忆并存，不知道哪条有效 | Zep（bi-temporal） | 第 5 章 |
| 记忆杂乱，想让它自己整理 | Mem0（extract-update） | 第 6 章 |
| 有一批信息该常驻但上下文装不下 | Letta / MemoryOS（分层） | 第 7 章 |
| 想统一管理多种表征 | MemOS（MemCube） | 第 7 章 |

**评估时要看的两件事**（第 10 章的判断方法）：

1. **可检视性**——你能不能看到它到底存了什么？一个你无法检查其内容的记忆系统，出问题时无法排错，合规时无法交代。
2. **删除路径**——它的删除是级联的吗？向量、图边、派生摘要都会处理吗（第 5 章 5.4.1、第 10 章 10.9.1）？

**⚠️ 不要用 star 数和 benchmark 分数做决定**，理由见本页开头。

**活跃度**：请自行查看各仓库的最近提交时间（GitHub 仓库页面直接可见）。本书不在此记录具体日期——那正是最容易过时的信息。第 10 章的质量红线提到：🕐 超过 6 个月无提交的项目，慎作生产依赖。

| 框架 | 记忆抽象 | 说明 |

| **Semantic Kernel** | Memory 抽象 + 多种 connector | .NET 生态友好 |

| **Pydantic-AI** | 消息历史为主 | 类型安全是它的卖点 |
| **OpenAI Agents SDK** | session 管理 | — |
| **Google ADK** | **Session（单次交互）/ Memory（长期库）** 明确分开 | 这个区分很清楚，值得借鉴 |
| **AgentScope**（阿里） | `memory` + `long_term_memory` 双组件 | 短期与长期分离 |

### 怎么用这张表

**Google ADK 和 AgentScope 的做法值得注意**：它们都把「本次会话的上下文」和「长期记忆库」明确分成两个概念。

这正是第 1 章 1.4 节强调的区分——**「把历史全拼进 prompt」是上下文管理，不是记忆系统**。框架在 API 层面就把两者分开，能避免大量混淆。

如果你用的框架没有这个区分，建议自己在应用层建立它。

| **AWorld**（蚂蚁） | 多智能体框架，含记忆组件 | — |
| **Camel-AI** | 多智能体框架 | 国际项目但中文社区活跃 |
| **TencentDB Agent Memory**（腾讯） | 托管记忆存储 | — |

### 怎么用这张表

**MemoryScope 值得实际读一读源码**——它是本书之外，中文语境里能找到的最完整的分层记忆开源实现。它的 consolidation 与 reflection 实现可以和本书第 6、8 章对照。

**关于百炼「记忆库」的数字**：🏢 那三个百分比是厂商自述。按第 10 章 10.4 节的五个问题去问——k 是多少？评判怎么做的？底座模型？成本？有无第三方复现？——公开信息里答不上来。**用它做参考，不要用它做决定。**

## B.6 商业产品的记忆功能

🕐🏢 这一节的信息变动最快，且几乎全部是厂商自述。

| 产品 | 机制（公开信息） | 说明 |
| :--- | :--- | :--- |
| **ChatGPT memory** | 后台隐式构建用户 profile | 具体机制未公开 |
| **Claude memory tool** | 2025-09-29 beta，`memory_20250818`；客户端文件系统 `/memory`，6 个 CRUD 命令；配合 context editing `clear_tool_uses_20250919` | 🏢 官方自述在内部 100 轮网搜任务上 84% token 节省、39% 性能提升。**架构上值得注意的一点**：记忆存在**客户端文件系统**，由模型通过工具调用读写——这和本书第 7 章的 self-editing memory blocks 是同一个思路 |
| **Gemini personalization** | 个性化记忆 | 具体机制未公开 |

### 怎么用这张表

**看架构，不看数字。**

Claude memory tool 的设计有一点值得学：**把记忆做成一个文件系统，让模型用工具调用去读写**。这个抽象很干净——它复用了模型已经很擅长的「操作文件」能力，而不是发明一套新的记忆 API。

至于 84%、39% 这类数字：🏢 厂商自述、特定任务、无第三方复现。按第 10 章的标准，它们**不能用作选型依据**。

## B.7 一张总的决策表

把全书的选型建议压缩成一张表：

| 你的情况 | 建议 | 章节 |
| :--- | :--- | :--- |
| 对话 < 30 轮，不需要跨会话 | **全历史注入**，别上记忆系统 | 第 1 章 1.9 |
| 需要跨会话，语料是自然语言 | 向量检索（dense 即可） | 第 3 章 |
| 记忆里有大量标识符（工单号、SKU） | 加 BM25 混合检索 | 第 3 章 3.4 |
| 多跳查询明显偏低 | 考虑图记忆，**先上规则抽取** | 第 4 章 4.8 |
| 状态会变且变化本身重要 | 双时间轴 + 失效 | 第 5 章 5.6 |
| 记忆杂乱、矛盾并存 | extract-update，**先算打平点** | 第 6 章 6.4.1 |
| 有一批信息该常驻但装不下 | 分层 + 热度换页 | 第 7 章 7.6 |
| 任务有重复模式 | 技能库 | 第 8 章 8.6 |
| 知识稳定、通用、不需溯源 | 可考虑参数化 | 第 9 章 9.5 |
| **任何时候** | **先建评测集** | 第 10 章 |

最后一行不是客套话。第 10 章开头那句话在这里再说一遍：

> **没有评测方法的优化，是在赌运气。**
