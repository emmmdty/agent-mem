# 第一章 为什么 Agent 需要记忆

> **本章目标**
>
> 1. 说清楚「记忆」在工程上到底指什么，以及它和上下文、RAG、微调的边界在哪。
> 2. 用三个可复现的实验，把「无记忆」「全塞进上下文」「检索」三条路的代价算出来。
> 3. 交代全书的分析框架——**表征 × 操作 × 载体**，并解释为什么不用流行的心理学四分法。
> 4. 写出主线项目 MiniMem 的第一块砖：`MemoryStore` 接口与 `BufferMemory`。
>
> **本章实验**：全部离线可跑，无需 API Key，总耗时约 5 秒。
>
> **前置知识**：Python 类与抽象方法。不需要了解 RAG。

## 1.1 从一次失败的对话说起

先跑一个实验。

```bash
python docs/chapter1/code/01_goldfish_agent.py
```

脚本让同一段 9 轮对话，分别经过三种不同的「历史处理方式」。对话内容很普通：

```
用户 > 你好，我叫小明。
用户 > 我在星辰银行工作，是一名信贷风控工程师。
用户 > 我对花生过敏，以后帮我点餐要注意。
用户 > 我喜欢周末去爬山。
用户 > 今天天气怎么样？
用户 > 帮我把这段话翻译成英文。
用户 > 推荐几部科幻电影吧。
用户 > 对了，我叫什么来着？        ← 回头题
用户 > 我对什么过敏？              ← 回头题
```

第一种方式是**每轮只把当前这句话发给模型**。结果：

```
  用户 > 对了，我叫什么来着？
  助理 < 抱歉，我不知道——你没有在我能看到的内容里提过这件事。  ❌
  用户 > 我对什么过敏？
  助理 < 抱歉，我不知道——你没有在我能看到的内容里提过这件事。  ❌
```

这个结果不该让人意外，但值得停下来想一秒：**模型并不是「忘了」，它是从来就没被告知过**。

> **关于实验用的模型**
>
> 本章实验用的是 `MockLLM`——一个只会做一件事的假模型：扫描传给它的消息，
> 用正则抽出其中的「属性 = 值」，能答就答，答不出就明说不知道。
>
> 为什么不用真模型？因为真模型在不知道答案时**往往会编一个**。
> 「小明」这个名字它可能瞎猜对，「花生过敏」它可能编成「海鲜过敏」。
> 幻觉会把「记忆有没有起作用」这个本该二值的问题搅成一团浆糊。
> MockLLM 不会编，它的每一次「不知道」都是可信的信号。
>
> 代价是它也不会推理、不会改写、不会归纳。所以从第 6 章起，
> 当我们需要 LLM 的判断力时，它会明确退场。

## 1.2 无状态不是缺陷，是设计

把一次 LLM 调用看成一个函数：

$$
\text{output} = f_\theta(\text{context})
$$

$\theta$ 是模型权重，一次推理里它是常量；`context` 是你这次传进去的全部内容。**同样的 context 进去，同样的 output 出来**（贪心解码下），与你上一次调用过什么毫无关系。

这不是工程上的偷懒，而是一个相当有价值的性质：无状态的服务可以随意水平扩展、可以在任意节点重放、可以被缓存。真正的问题在于——如果模型本身不保存状态，那么「记住」这件事必须发生在别的地方。

**只有三个地方可以放**：

| 放在哪 | 怎么写进去 | 怎么读出来 | 本书章节 |
| :--- | :--- | :--- | :--- |
| **模型权重里**（参数化） | 训练、微调、模型编辑 | 直接生成，无需检索 | 第 9 章 |
| **本次上下文里**（上下文-非结构化 / 结构化） | 拼进 prompt | 模型自己注意到 | 第 2~8 章 |
| **外部存储里** | 写入数据库/文件 | 检索后拼进 prompt | 第 3~8 章 |

注意第二行和第三行的关系：**外部存储最终也要经由上下文才能被使用**。没有第四条路。所谓「给 Agent 加记忆」，本质上都是在回答同一个问题：

> 在有限的上下文预算里，这一轮应该放进去哪些信息？

这个问题贯穿全书。第 2 章讨论「上下文能有多大、放不下时丢什么」，第 3~6 章讨论「怎么挑」，第 7 章讨论「怎么在多层存储之间调度」，第 10 章讨论「怎么知道挑得好不好」。

## 1.3 「全塞进去」要付四笔账

既然要放进上下文，最直接的做法就是——**全放**。每轮把此前所有对话原样重发。

实验一里这个方案答对了全部两道回头题。它简单、无损、没有检索误差。事实上对于短对话，它就是最优解，本书不建议你为了「显得专业」而给一个只有二十轮的客服机器人上向量库。

但它要付四笔账。

### 第一笔：成本是二次增长的

```bash
python docs/chapter1/code/02_context_cost.py
```

```
  策略                    10 轮        50 轮       100 轮       500 轮
  --------------------------------------------------------------
  无记忆                    570       2,850       5,700      28,500
  全历史注入                4,755     116,775     466,050  11,630,250
  滑动窗口                 4,755      76,320     172,170     938,970
  检索 top-k             1,674       9,474      19,224      97,224
```

第 $n$ 轮要发送的 token 数正比于 $n$，那么 $N$ 轮对话的累计输入就是：

$$
\sum_{n=1}^{N} n \cdot c = \frac{N(N+1)}{2} \cdot c = O(N^2)
$$

**轮数翻倍，账单翻四倍**。500 轮时，全历史方案的累计输入 token 是检索方案的约 120 倍。

这个数字有几个必须说明的前提：它只算了输入侧；它假设每轮长度相同；它没有考虑 prompt 缓存（主流 API 大多对重复前缀有折扣，实际账单会低于这个估算，但增长的**阶**不变）。所以请把它当作量级参考，不是账单。

### 第二笔：上下文窗口有硬上限

窗口再大也是有限的。而且撞上限的方式往往很难察觉：多数推理服务在超长时会**静默截断**，通常从最前面开始丢。

于是产生一类经典 bug——用户在对话开头说的「我对花生过敏」，在第三百轮时已经不在窗口里了，而系统日志一切正常，模型也没有报错，它只是给出了一个「合理」的、含花生的推荐。

`MockLLM` 刻意模拟了这个行为（`context_limit` 参数，从最旧的消息开始丢），第 2 章会用它做一个专门的实验。

### 第三笔：长上下文不等于长上下文用得好

即使窗口塞得下，模型也未必用得好。

> 📄 Liu et al. 的 *Lost in the Middle*（arXiv:2307.03172，TACL 2024）系统地测量了这一现象：当关键信息位于长输入的**中部**时，模型的检索准确率明显低于它位于开头或结尾时，形成一条 U 形曲线。这个结论在多个模型上成立。

后续的长上下文基准（RULER、HELMET、∞Bench、LongBench 系列，见第 10 章）也反复表明：**「窗口长度」和「有效使用长度」是两回事**，前者是规格，后者要测。

### 第四笔：跨会话、多用户、可编辑性

前三笔是技术账，第四笔是产品账，而且往往是决定性的：

- **跨会话**：用户关掉 App 明天再来，昨天的上下文没了。你需要一个比「本次会话」活得更久的东西。
- **多用户**：一份历史属于一个用户。跨用户串味在合规上是事故，不是 bug。这就是为什么本书的接口从第一行起就带 `user_id`。
- **可编辑与可删除**：用户说「忘掉我刚才说的地址」，你需要能**定位并删除**那条信息。一大团拼接的历史文本做不到这件事。GDPR 与个人信息保护法下的删除权要求的是真删除，不是「不再检索」（第 10 章展开）。
- **可审计**：模型为什么这么答？如果记忆是一段无结构的历史，你无法回答；如果是一条条带来源的记录，你可以（第 5 章的 provenance）。

> **误区预告**：「长上下文杀死了 RAG」和「RAG 让长上下文没有意义」这两句话都错。
> 它们在**成本、延迟、更新频率、可审计性**上的取舍完全不同，实践中通常是组合使用。
> 第 2 章末尾会给出一张对照表，第 10 章会给出实测方法。

## 1.4 记忆的工程定义

到这里可以给出本书使用的定义了：

> **记忆（memory）**：在单次上下文之外持久化、能被**有选择地**取回并注入上下文的信息，
> 以及围绕它的一整套操作（写入、组织、检索、更新、遗忘）。

三个限定词都不多余：

- **单次上下文之外**——所以「把历史全拼进 prompt」不算记忆系统，它只是上下文管理。
- **有选择地取回**——所以「把整个数据库都塞进去」也不算，选择性是记忆的核心难点。
- **一整套操作**——所以「存进向量库」只完成了八分之一的工作。大量系统的问题不在于存不下，而在于存进去之后**从不更新、从不遗忘、从不整理**。

和几个相邻概念的边界：

| | 存在哪 | 更新代价 | 可删除 | 典型延迟 | 本书章节 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **上下文工程** | 本次 prompt | 无（每次重建） | 不适用 | 无额外 | 第 2 章 |
| **RAG** | 外部知识库 | 低（改文档即可） | 是 | 检索一次 | 第 3、4 章 |
| **Agent 记忆** | 外部存储 | 低到中（可能需 LLM 抽取） | 是 | 检索 + 可能的写入处理 | 第 3~8 章 |
| **微调 / 模型编辑** | 模型权重 | 高（需训练） | 困难 | 无额外 | 第 9 章 |

**RAG 和 Agent 记忆的差别常被问到**，这里说清楚：技术栈高度重叠（都要切分、嵌入、检索），差别在**数据的性质**。

- RAG 的语料通常是**外部的、相对静态的、多用户共享的**（产品手册、法规、论文）。
- 记忆是**用户产生的、持续变化的、必须隔离的**（他说过什么、他改主意了、他要求删除）。

这个差别直接导致：记忆系统必须处理 RAG 通常不处理的三件事——**时间**（第 5 章）、**冲突与更新**（第 5、6 章）、**权限与遗忘**（第 10 章）。技术上你可以用同一个向量库，但如果你把记忆当成 RAG 来做，一定会在这三件事上翻车。

## 1.5 分类法之争：为什么本书不用心理学四分法

打开任何一篇 Agent 记忆的介绍文章，大概率会看到这四个词：

- **工作记忆**（working memory）：当前正在处理的信息
- **情景记忆**（episodic memory）：发生过的具体事件
- **语义记忆**（semantic memory）：抽象出来的一般知识
- **程序记忆**（procedural memory）：怎么做某件事的技能

这套划分来自认知心理学（Tulving 对情景/语义记忆的区分是其经典源头），它有直觉上的吸引力：人的记忆确实像是分成了这些类别，把 Agent 类比成人显得优雅。

**但把它当作系统的模块划分，会误导实现。** 三个理由。

### 理由一：落到代码里，它们大多只是标签

看看实际系统里这四个词对应什么：

| 心理学术语 | 代码里通常是 |
| :--- | :--- |
| 工作记忆 | 当前 prompt 里的那几千个 token |
| 情景记忆 | 一张带时间戳的对话记录表 |
| 语义记忆 | 一张抽出来的事实表 |
| 程序记忆 | 一个存代码片段或 SOP 的文件夹 |

四个"类型"用的是同一套存储、同一套检索、同一套接口。真正不同的是**里面存了什么内容**——而内容差异不构成模块边界。你不会因为一张表存的是订单、另一张存的是用户，就说自己实现了「两种数据库」。

### 理由二：最关键的那个过程，在多数系统里并不自动

四分法最有价值的部分其实是它暗示的**转化关系**：情景记忆经过**巩固（consolidation）**变成语义记忆——你不需要记得每一次开会，只需要记得「小明是风控工程师」。

问题是，在绝大多数已发布的系统里，这个转化**不是自动发生的**。它要么由固定规则触发（每 N 轮跑一次），要么需要显式调用一个「请从以下对话中抽取事实」的 prompt，要么干脆由开发者手动调用 API。

> ⚠️ 相关综述中有类似判断（如报告中提及的 *Memory for Autonomous LLM Agents*，arXiv 编号 2603.07670 系检索结果所载、本书未独立核实）。
> 但这一点无需依赖二手引用——你在第 6 章会亲手实现一次 extract-update 流水线，
> 然后你会发现：**决定何时触发巩固，是一个纯粹的工程启发式问题**，
> 目前没有任何一种「自动」机制能免于人工设定阈值。

一个类比：如果说明书上写着「本系统具备情景记忆到语义记忆的巩固能力」，而实现是「每 20 轮调用一次抽取 prompt」，那么描述它的准确说法是「定时批量抽取」，而不是一个认知过程。前者可以调参、可以测成本；后者只能让人点头。

### 理由三：主流综述自己就没用这套划分

三篇有代表性的工作，用了三套不同的分类轴：

| 工作 | 分类轴 | 说明 |
| :--- | :--- | :--- |
| 📄 Zhang et al.，*A Survey on the Memory Mechanism of LLM-based Agents*（arXiv:2404.13501，后收入 ACM TOIS，DOI 10.1145/3748302） | **来源 / 形式 / 操作** | 第一篇专门面向 agent memory 的系统综述 |
| 📄 Du et al.，*Rethinking Memory in AI: Taxonomy, Operations, Topics, and Future Directions*（arXiv:2505.00675） | **表征 × 操作** | 表征三分：参数化 / 上下文-结构化 / 上下文-非结构化；定义六种原子操作 |
| 📄 MemOS 系列（arXiv:2505.22101 短文，arXiv:2507.03724 长文） | **参数化 / 激活 / 明文** | 提出 MemCube 抽象，把三类记忆统一封装 |

它们连**「KV cache / 隐状态算不算一类独立的记忆」**都没有共识：Du 等人把它归入上下文类，MemOS 则把「激活记忆」单列一类。

这不是坏事——分类法本来就是为了解决特定问题而设计的工具。但它说明一件事：**没有一个权威的、公认的记忆分类法**。既然如此，本书选择一套**对写代码最有用的**。

### 本书采用的三轴

```
表征（记忆存在哪里）              操作（对记忆做什么）           载体（用什么存）
├─ 参数化 parametric             ├─ 编码 Encoding              ├─ 内存 / 文件
│    权重里，第 9 章               ├─ 巩固 Consolidation         ├─ 向量库
├─ 上下文-非结构化                 ├─ 索引 Indexing              ├─ 图库
│    原文 / 摘要，第 2、3 章        ├─ 检索 Retrieval             ├─ 关系库
└─ 上下文-结构化                   ├─ 更新 Updating              └─ 模型权重
     图 / 表 / 技能，第 4~8 章      ├─ 遗忘 Forgetting
                                 ├─ 压缩 Compression
                                 └─ 反思 Reflection
```

它比四分法好用在三点：

1. **每一章可以聚焦一种操作**，章节边界和代码模块边界一致。
2. **表征三分能干净地切开技术路线**：长上下文（非结构化）、图记忆（结构化）、模型编辑（参数化）分属不同章，不重叠。
3. **载体是可替换的**：同一种表征可以换不同的库来存，这让「选型」成为一个独立于「机制」的问题（附录 B 专门处理）。

心理学四分法在本书中只出现在这一节，作为**类比**和**术语对照**保留（附录 D 术语表会给出对照关系），不再作为骨架使用。

> **本书的用词纪律**：`episodic` / `semantic` 这类词在描述具体实现时会被替换为它实际的含义。
> 比如不说「我们实现了情景记忆」，而说「我们存了带时间戳的原始消息」。
> 这不是咬文嚼字：前者听起来实现了一个认知过程，后者才是你要维护的那张表。

## 1.6 八种操作，八个章节的地图

Du 等人定义了六种原子操作，本书在此基础上补充「编码」与「反思」两项（前者是写入的必经步骤，后者在经验型记忆里独立成一类机制），凑成八种。

| 操作 | 它在回答什么问题 | 典型实现 | 主要章节 |
| :--- | :--- | :--- | :--- |
| **编码** Encoding | 原始信息怎么变成可存的形式？ | 切分、嵌入、实体抽取 | 第 3、4 章 |
| **巩固** Consolidation | 零散记录怎么变成稳定的知识？ | 摘要、事实抽取、聚类建树 | 第 4、6 章 |
| **索引** Indexing | 怎么在不扫全表的情况下找到？ | 向量索引、倒排、图邻接 | 第 3、4 章 |
| **检索** Retrieval | 这一轮该取回哪几条？ | 相似度、混合检索、重排、PPR | 第 3、4 章 |
| **更新** Updating | 新信息与旧记忆冲突时怎么办？ | extract-update、事实失效 | 第 5、6 章 |
| **遗忘** Forgetting | 什么该被丢掉？ | 时间衰减、容量淘汰、主动删除 | 第 5、7、10 章 |
| **压缩** Compression | 放不下时怎么少占地方？ | 摘要、KV cache 驱逐、分层 | 第 2、7 章 |
| **反思** Reflection | 怎么从经验里长出新东西？ | 反思 prompt、技能归纳 | 第 8 章 |

这张表也是本书的导航图：**当你在实践中遇到问题，先判断它属于哪个操作，再去对应章节**。

比如「用户改了偏好但 Agent 还在用老的」——这是更新问题，去第 5、6 章；「检索总是返回一堆不相关的」——这是检索问题，去第 3 章；「记忆库越来越大越来越慢」——索引或遗忘问题，去第 3、7 章。

## 1.7 动手：MemoryStore 接口

现在写第一块砖。全书所有记忆实现都会实现同一个接口——这是**本书结构上最重要的一个决定**，理由很简单：

> **不能被比较的方案，等于没有结论。**

如果第 3 章的向量记忆和第 7 章的分层记忆各有各的 API，那到第 10 章就没法把它们放进同一个评测里，全书就退化成八篇互不相干的介绍文。

接口本身很小：

```python
class MemoryStore(ABC):
    def add(self, item: MemoryItem | str, *, user_id: str) -> str: ...
    def search(self, query: str, *, user_id: str, k: int = 5) -> list[SearchResult]: ...
    def update(self, memory_id: str, patch: dict, *, user_id: str) -> None: ...
    def delete(self, memory_id: str, *, user_id: str) -> None: ...
    def all(self, *, user_id: str) -> list[MemoryItem]: ...
```

完整实现见 [`minimem/base.py`](https://github.com/emmmdty/agent-mem/blob/main/minimem/base.py)。这里说三个值得解释的设计决策。

### 决策一：`user_id` 是必填的，越权抛异常

```python
@staticmethod
def _check_user_id(user_id: str) -> None:
    if not isinstance(user_id, str) or not user_id.strip():
        raise ValueError("user_id 必须是非空字符串；记忆库不允许匿名读写")
```

而越权访问抛的是异常，不是返回空：

```python
if owner != user_id:
    raise CrossUserAccessError(f"记忆 {memory_id} 不属于用户 {user_id}")
```

为什么不静默返回空？因为**静默失败会让越权访问的 bug 一直藏到线上**。返回空看起来"更安全"，实际上是把一个本可以在测试阶段暴露的逻辑错误，变成了一个只在生产环境的日志里表现为「用户偶尔查不到自己记忆」的幽灵问题。

（这里有一个真实的权衡：对**外部 API** 而言，区分「不存在」和「无权访问」等于确认了 ID 的存在性，可能被用来枚举。所以生产系统通常在内部抛异常、在边界统一转成 404。第 10 章会再谈。）

### 决策二：公开方法负责计量，子类只写逻辑

```python
def search(self, query: str, *, user_id: str, k: int = 5, **kwargs) -> list[SearchResult]:
    self._check_user_id(user_id)
    if k <= 0:
        raise ValueError(f"k 必须为正整数，收到 {k}")

    with self._meter.measure(op="search", store=self.name, user_id=user_id) as rec:
        results = self._search(query, user_id=user_id, k=k, **kwargs)
        rec.n_items = len(results)
    return results
```

这是模板方法模式：`search` 是公开的、被计量的；`_search` 是子类实现的、纯逻辑的。

好处在第 10 章才完全兑现——`EvalHarness` 不需要给八种实现分别写埋点，所有方案的延迟、token、调用次数都以同样的方式被记录下来。**「代价必须一等呈现」这条原则，在架构上就是这么落实的**，而不是靠写文档时提醒自己。

`Meter` 的实现见 [`minimem/utils/metering.py`](https://github.com/emmmdty/agent-mem/blob/main/minimem/utils/metering.py)，一百行左右。注意它记录失败路径：

```python
except Exception as exc:
    rec.extra["failed"] = type(exc).__name__
    raise
finally:
    rec.duration_ms = (time.perf_counter() - t0) * 1000
```

如果失败的操作不计时，那么「超时率高的方案」会显得比实际更快——它最慢的那些请求全都从统计里消失了。

### 决策三：新信息进 `metadata`，不进字段

```python
@dataclass
class MemoryItem:
    content: str
    id: str = field(default_factory=_new_id)
    created_at: datetime = field(default_factory=_now)
    kind: str = "message"
    metadata: dict[str, Any] = field(default_factory=dict)
    user_id: str | None = None
```

只有六个字段。后面章节需要的一切——向量、实体列表、有效期、热度、访问计数、技能签名——全部放进 `metadata`。

否则到第 8 章，这个类会有三十个字段，其中二十五个对任何一个具体实现都是 `None`。

有一个字段值得单独说：`created_at` 记录的是**写入时间**，不是事实的**发生时间**。「我下个月入职长风科技」这句话的写入时间是今天，生效时间是下个月。把两者混为一谈，是时序问答出错的头号原因——第 5 章会为此引入双时间轴。

### `BufferMemory`：最朴素的实现

```python
class BufferMemory(MemoryStore):
    """按写入顺序保存全部记忆，检索用词重叠打分。"""
```

它的检索逻辑只有几行：把查询和每条记忆都切成字符集合，算 Jaccard 相似度，再混一点新近性权重：

$$
\text{score} = (1-w) \cdot \frac{|Q \cap M|}{|Q \cup M|} + w \cdot \text{recency}
$$

这个设计是有来历的。📄 Generative Agents（Park et al., UIST 2023, DOI 10.1145/3586183.3606763）的记忆流用的是 **recency / relevance / importance** 三项加权。这里先实现前两项，`importance` 需要 LLM 打分，留到第 8 章。

`BufferMemory` 有两个不可替代的价值，请不要因为它简单就轻视它：

1. **它常常够用**。几十轮的对话里，它的效果就是最好的，而且没有任何检索误差引入的风险。
2. **它是代价的下界**。零 LLM 调用、零嵌入计算、零外部依赖。后面每一章新增的机制，都必须回答一个问题：**比 BufferMemory 多花的这些钱，换来了什么？**

## 1.8 三堵墙

```bash
python docs/chapter1/code/03_buffer_walls.py
```

`BufferMemory` 能用，但会在三个地方撞墙。这三堵墙恰好对应后面九章的全部内容。

### 墙一：语义鸿沟

```
  查询                  命中                                  是否正确
  ------------------------------------------------------------------
  我做什么工作？             我从事信贷风险评估工作，主要看制造业客户。               ✅
  他的职业是什么？            我们家的猫叫毛毛，今年三岁。                      ❌
  我养宠物了吗？             我们家的猫叫毛毛，今年三岁。                      ✅
  我最近旅游去哪了？           最近在读《证券分析》。                         ❌
```

「我做什么工作？」命中是因为共享了「我、工作」两个字——运气。「他的职业是什么？」与目标记忆一个字都不共享，于是彻底失败。

这不是参数没调好。**字面匹配匹配的是字符，不是意思**。中文里同一件事的表述方式多到无法穷举（职业 / 工作 / 干什么的 / 从事什么 / 是做啥的），靠维护同义词表补不完这个洞。

→ 第 3 章用句向量把「意思」变成可计算的向量，推倒这堵墙（然后你会看到它立起一堵新的：语义相近不等于能回答问题）。

### 墙二：规模天花板

```
  记忆条数        单次检索均值(ms)          相对 100 条      每天 1 万次查询的耗时
  --------------------------------------------------------------------------
  100         0.29                1.0×                    0.00 小时
  1,000       2.91                9.9×                    0.01 小时
  5,000       15.50               52.9×                   0.04 小时
  20,000      66.38               226.5×                  0.18 小时
```

严格线性。原因很直白：每次检索都要把该用户的全部记忆扫一遍。

两万条听起来很多吗？一个每天聊 50 轮的用户，一年就积累一万八千条。而这只是**一个**用户。

→ 第 3 章引入向量索引把复杂度降下来；第 7 章引入分层，让绝大多数记忆待在不参与检索的冷层里。

> 这组数字来自单机 Python 实现，绝对值没有普适意义（你的机器上会不同）。
> 有意义的是**斜率**：它是线性的，而线性在这里就是不可接受的。

### 墙三：知识演化

用户按时间顺序说了这些：

```
    1. 我在星辰银行工作。
    2. 今天开了一天的会。
    3. 我下周就要从星辰银行离职了。
    4. 新工作定了，我下个月入职长风科技。
    5. 周末去看了场电影。
```

问「我在哪工作？」，`BufferMemory` 召回：

```
    · 我在星辰银行工作。（分数 0.356）
    · 新工作定了，我下个月入职长风科技。（分数 0.291）
    · 周末去看了场电影。（分数 0.200）
```

三处问题，一个比一个严重：

1. **两条互相矛盾的事实同时出现**，谁新谁旧无从判断。
2. **真正解释了矛盾的那条（「我下周就要从星辰银行离职了」）没有被召回**——它和查询几乎没有字面重叠。
3. **一条完全无关的记录凑数进了 top-3**——因为 `k=3` 是写死的，够不够都要凑满。

而且第 4 条说的是**未来才生效**的事。如果今天还没到下个月，正确答案仍然是星辰银行。

`BufferMemory` 对此完全无能为力，因为它只做了一件事：把说过的话原样存下来。它没有判断事实失效（→ 第 5 章）、没有区分记录时间与生效时间（→ 第 5 章）、没有把多条消息归纳成一条当前有效的事实（→ 第 6 章）、也不会根据召回质量动态决定取几条（→ 第 3 章）。

**把矛盾信息一股脑塞给模型让它自己判断**——这是相当多系统的实际做法，也是长对话中「模型说法前后不一」的主要来源之一。

### 三堵墙与三根轴

```
    语义鸿沟   → 表征问题：怎么把「意思」变成可计算的东西    → 第 3、4 章
    规模天花板  → 索引与调度问题：怎么不扫全表              → 第 3、7 章
    知识演化   → 操作问题：怎么更新、失效、遗忘             → 第 5、6 章
```

这三个方向恰好落在「表征 × 操作 × 载体」三根轴上。这不是巧合，而是这套分类法值得用的原因：**它能把你实际遇到的问题，直接映射到该读哪一章**。

## 1.9 代价与选型

本章三种方案的横向对比（本书每章末尾都会有这样一张表）：

| 方案 | 写入代价 | 检索代价 | 单轮 prompt token | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 无记忆 | 0 | 0 | 最小 | 单轮工具调用、无状态 API |
| 全历史注入 | 0 | 0 | 随轮数线性增长 | **< 30 轮的短对话**，最优选择 |
| `BufferMemory` + top-k | O(1) | O(N) 全扫描 | 常数 | 教学基线；条数 < 1000 的小场景 |

**给实践者的建议**：不要一上来就上向量库。先问三个问题——

1. 对话平均多少轮？**如果不到 30 轮，全历史注入几乎肯定是更好的选择**，它没有检索误差、没有额外组件、没有运维成本。
2. 需要跨会话吗？如果不需要，你要的可能只是会话内的上下文管理（第 2 章），不是记忆系统。
3. 你能测出改进吗？如果没有一个能比较「加了记忆之后好多少」的方法，那么加什么都只是心理安慰。第 10 章的 harness 值得先于第 3 章读。

## 1.10 常见误区

**误区一：「记忆 = 把历史全塞进上下文」**

那是上下文管理。记忆的核心难点是**选择性**——在有限预算里挑该带的那几条。全塞进去恰恰是放弃了选择。

**误区二：「上下文窗口够大就不需要记忆了」**

窗口大小解决不了跨会话、多用户隔离、可删除、可审计这四个问题，也解决不了成本的二次增长。而且 📄 *Lost in the Middle*（arXiv:2307.03172）表明，塞得下不等于用得好。

**误区三：「先按情景/语义/程序记忆把模块分好」**

这套划分不构成模块边界（1.5 节）。按它分模块，你会得到三个内部几乎一样的类，以及一个谁也说不清什么时候该跑的「巩固」函数。

**误区四：「向量库 = 记忆系统」**

向量库只提供了八种操作里的两种（索引、检索）。更新、遗忘、巩固、反思一个都没有。大量项目的记忆问题不是「存不下」，而是**存进去之后再也没有整理过**。

**误区五：「用了 LLM 抽取，记忆就变准了」**

LLM 抽取会引入新的错误来源：抽错、抽漏、把假设当事实。而且每次抽取都是真金白银。第 6 章会把这笔账算清楚，包括抽取失败时系统会怎样。

## 1.11 小结

- LLM 单次调用是无状态的纯函数，「记住」只能发生在权重里、上下文里或外部存储里，而后两者最终都要经由上下文起作用。
- 「全历史注入」在短对话里是最优解，但要付四笔账：成本二次增长、窗口硬上限、长上下文质量衰减、跨会话与合规问题。
- 记忆的工程定义是「单次上下文之外持久化、可被有选择取回并注入的信息，以及围绕它的一整套操作」。**选择性**和**一整套操作**是两个关键限定。
- 本书用**表征 × 操作 × 载体**三轴，不用心理学四分法——后者在代码里大多只是标签，且其最有价值的「巩固」过程在现有系统里并不自动。
- `MemoryStore` 的三个设计决策：`user_id` 必填且越权抛异常、公开方法统一计量、扩展信息走 `metadata`。
- `BufferMemory` 撞的三堵墙——语义鸿沟、规模天花板、知识演化——正是后面九章的地图。

下一章进入**上下文本身**：窗口放不下时到底该丢什么，为什么「丢最旧的」是最糟糕的默认策略，以及长上下文技术（StreamingLLM、Titans、KV cache 压缩）到底解决了什么、没解决什么。
